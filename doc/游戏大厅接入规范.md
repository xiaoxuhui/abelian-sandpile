## 工作边界（用户明确要求）

本窗口只负责阿贝尔沙滩单个游戏。可开发游戏规则、关卡、界面、存档与文件导出适配，验证自己的离线资源、子路径和存储前缀，并交付接入资料。

大厅功能扩展、第五来源注册、原生桥注册、卡片布局、签名下载、合集构建/发布及其它游戏回归由大厅项目负责。本文件只记录宿主依赖，不授权本窗口实施它们；游戏是否完成与大厅是否已扩展分开报告。

## 1. 当前已经实施的约束

| 项目 | 本游戏应满足 | 当前宿主事实 |
| --- | --- | --- |
| 游戏 ID | 候选永久 ID `abelian-sandpile` | 格式允许小写字母/数字/短横线，但锁文件校验只接受四个固定 ID |
| 来源版本 | 公开源地址已创建，正式消费时锁定 40 位 SHA 和精确版本 | 构建脚本拒绝浮动分支与版本不匹配 |

| 文件导出 | 浏览器标准导出；未来通过确认过的能力适配 | 四个旧桥名称按固定 ID 映射，第五个尚未注册 |
| 离开页面 | 自身保存完整状态；恢复默认暂停 | 返回大厅销毁当前 WebView，不保留长驻 JS 任务 |
| 来源保护 | 大厅独立检出并只读消费固定来源 | 本地来源模式要求准确 SHA 且工作树干净 |

候选网页 URL：`https://appassets.androidplatform.net/assets/games/abelian-sandpile/index.html`。它是计划地址，当前 APK 没有这个入口。

## 2. 本项目提供的候选合约

`game-hub.integration.json` 记录游戏 ID、名称、版本、静态入口、资源白名单、许可、实际存储键与已实现的游戏存档合同。源仓库已创建为 `https://github.com/xiaoxuhui/abelian-sandpile.git`；正式消费 SHA 尚未选定，宿主兼容范围仍为 null，不冒充已经存在的发行身份。

根目录运行文件采用 static 可复制布局；`dist/asset-manifest.json` 为项目自身构建结果的字节数/摘要清单，不是 `catalog.signed.json` 或大厅 bundle manifest。未来接入时大厅重新生成自己的完整摘要清单。

## 3. 大厅项目负责的外部前置条件（本窗口不实施）

1. 独立规划第五游戏：修改 sources.lock.json 并扩展 validateLock 中四来源数量/固定 ID 集合。
2. 更新原生卡片布局、图标注册与 bridgeName；缺图或未知桥不能掩盖为已接入。
3. 增加入口、资源完整性、第五存储前缀、许可/通知及 APK 包内容检查；verify_apk.py 当前同样固定四来源。
4. 验证浏览器子路径、WebView 离线、系统返回、导出/导入、旋转与杀进程恢复。
5. 同 origin 设置全部游戏哨兵数据，逐个重置，证明其它项目数据保留；再跑原有四游戏核心回归。
6. 在授权的正式来源 SHA 上独立组装候选；补游戏实际版本、许可和源信息，再决定发行。

这轮没有修改来源锁文件、原生桥、APK、签名材料或大厅版本。

## 4. v0.3.0 与动态扩展的边界

大厅 v0.3.0 的资源更新文档仍是规划，并且 `games` 仍要求四固定 ID；动态新增游戏被放在之后阶段，统一原生桥和目录协议尚未确定。

新项目可以提前准备存档合同、可重复产物、SHA、入口和名称等信息；不能因此生成“已签名目录”、声明自动下载已支持或填写未经测试的 min/max hostVersionCode。未来要求的 contentCode、resourceProtocol 和双向存档兼容性须由宿主协议及实测证据决定。
