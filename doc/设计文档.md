# 阿贝尔沙滩：设计文档

## 1. 文档信息

- 版本：V0.1；日期：2026-10-08（Asia/Shanghai）。
- 状态：初版设计草案；当前只实施工程骨架。
- 需求依据：[需求与测试用例](需求与测试用例.md)。
- 开发流程：`build-tested-mini-app` 与 `plan-driven-frontend-dev`，沿用 EML 的文档、测试及提交纪律。
- 工作边界：只开发本游戏；大厅代码、扩展注册、宿主原生桥、合集构建/发布均由大厅项目负责。
- 迭代划分见[版本迭代规划](版本迭代规划.md)；v0.1.0 计划先完成两模式与存档的最小可玩闭环，当前仍只有工程骨架。

## 2. 设计目标

1. 领域规则不依赖 DOM、Canvas、存储或宿主桥，可在 Node 中独立验证。
2. 两种模式复用同一数学引擎；挑战模式只约束输入并判定目标。
3. 粒数、崩塌和流失统计可核对；性能优化不改变物理规则。
4. 无运行时外网依赖，可直接打开构建产物或置于大厅子路径。
5. 版本化存档、独立存储前缀、可重复资源清单和可审计文档为后续开源/大厅接入铺路。

## 3. 分层与目录


实际骨架目录：`src/`、`src/domain/`、`src/storage/`、`data/challenges/`、`tests/`、`scripts/`、`doc/`、`dist/`、`release/`。

## 4. 模型、计数与执行

- 使用一维行优先 `cells[y * width + x]`，对外存档是普通整数数组。内部容器选择须先确定数值上限，不把 Uint32 溢出当成合法回绕。
- `rules` 固定标识 `square4-open-v1`，记录阈值 4、四方向和开放耗散边界。
- 引擎只接受校验后的操作，返回新状态或受控修改结果及计数；错误操作不得部分写入。
- 单步采用双缓冲同步波：读取轮初棋盘、积累增量、一次提交。
- 快速稳定化可采用工作队列、批量合法崩塌；以朴素参考引擎对小棋盘随机输入做交叉验证。
- 基础崩塌计数累加真实次数，不用渲染帧数替代。每轮检查质量账本；开发验证可记录逐格 odometer，用于顺序无关性质验证。
- 主线程按预算分帧并允许中止；是否引入 Worker 由实测决定。若使用 Worker，文件必须进白名单并采用相对 URL，不能假设所有 file:// 场景支持。
- `generationId` 随重置、预设、导入、模式切换递增；旧异步回调检查编号后丢弃，避免覆盖新局。
- UI 用显式状态 `paused / running / stabilizing / stable / error`，稳定性由棋盘决定，运行性由调度器决定。

成熟库选择：当前未找到需要作为骨架依赖的既定引擎。实现前评估可用沙堆库的规则、许可、离线体积和兼容性；若采用自研，记录选择依据，保留朴素参考引擎和性质测试，不在本轮锁死引擎实现。

## 5. 挑战数据草案

`data/challenges/example.json` 用于讨论字段：

```text
schemaVersion, gameId, status, id, version, title, description,
rules, board: {width, height, initial, target},
allowedDropCells: [{x, y}], grainPerMove, maxMoves,
referenceMoves: [{x, y}], proofStatus
```

示例为 3×3 中心 3 粒，再投一粒产生十字。`status=draft`、`proofStatus=unverified`，骨架只验证结构，不宣称已验证可解性。

关卡数据不能携带脚本、HTML 或任意资源 URL；展示文本用 textContent。求解器逐层广搜，动作后稳定化，合法位置从该关数据生成。正式发布前验证参考路径、所有目标稳定性、预算内可达性；声明最优步数时必须穷举到首次命中层。

## 6. 存档草案与恢复

候选实验 JSON：`schemaVersion=1`、`gameId=abelian-sandpile`、`rules=square4-open-v1`、棋盘尺寸/粒数数组、初始总量/投入/流失/崩塌统计、模式和展示设置。

挑战进度另存关卡 ID/版本、已验证完成状态和个人最好步数；进行中关卡只写完整稳定快照。长驻任务不持久化，恢复默认暂停。

导入先在临时对象中校验，再替换并保存；存储失败保持内存现场。清空只删除本游戏具体键。存档合同草案 `abelian-sandpile-save-v1` 尚未发行，未来大厅资源回退只有双向兼容证据齐全才能宣称兼容。

## 7. 界面与无障碍

拟议玩法 UI：顶部模式/运行状态；主区棋盘；侧区投沙与速度；下方统计/图例；挑战模式显示目标预览、步数、重置/撤销。

移动端改为单列，关键控制至少 44px 可点击高度；Canvas 尺寸受容器约束并按 DPR 调整。键盘选格和文字显示弥补纯颜色表达；动画不会在恢复页面后自动启动。

工程占位页只展示当前交付状态、两种模式概要及接入注意事项，禁止放可点击却无行为的“开始游戏”按钮。

## 8. 构建与大厅边界

骨架使用 Node 内置测试和文件 API，零第三方依赖。`node scripts/build.mjs` 将固定运行时文件和 MIT 许可复制到 dist，生成 `asset-manifest.json`，记录入口、版本、文件字节数和 SHA-256。清单不写时间戳或绝对路径；它是本项目构建清单，不是大厅签名目录。

`game-hub.integration.json` 是候选来源合约，既不是可直接插入 `sources.lock.json` 的条目，也不是已经生效的大厅协议。静态来源可由大厅 `buildKind=static` 打包根目录文件；同时 dist 供独立预览。由于大厅 static 不自动构建来源，不把 dist 假装成已兼容的新 buildKind。

当前大厅限制四个固定 ID；锁文件校验扩展、卡片/icon 注册、导出桥映射、宿主审计、Android 入口、APK 校验及全部游戏回归，均由大厅项目负责。本项目只交付游戏端的资源、存档、许可与兼容证据。见[游戏大厅接入规范](游戏大厅接入规范.md)。

## 9. 骨架阶段验证

- Node 工程测试：必需文档与许可、规划字段、草案数据结构、相对离线资源、元信息一致、资源摘要、重复构建一致性。
- 真实浏览器：占位页打开、两种模式说明切换、键盘点击、桌面/移动布局，以及大厅形状子路径预览。
- 骨架测试不替代 U01–U24 的领域与存档测试；Android 设备验收当前不适用。
